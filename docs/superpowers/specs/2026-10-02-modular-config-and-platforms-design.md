# 功能选择、通道顺序与跨平台设计

日期：2026-10-02

状态：供用户核对的设计，尚未实现或激活

基线：`codex/full-python-port`，`d2c4e38`

## 1. 用户要求与完成标准

软件要让用户按需选择功能、供应商和通道。未选择且不属于已选功能必需依赖的部分，不安装依赖、不检查凭据、不启动进程、不发网络请求。无须生成删减源码的发行包。

开窗与额度查询分别保存有序的通道列表。单通道列表就是关闭 fallback；失败时不得暗中加入其他通道。允许 Pi 优先，也允许原生 Codex、原生 agy 或直接 API 优先。

Pi 实时查询额度必须只有认证和额度元数据请求，不发模型请求。旧的 Pi 快照仍可单独选用，但不能冒充实时查询。

当前用户的已安装配置作为个人配置保留。它不作为新用户默认值，新增通道也不得自动加入它。

跨平台目标是 macOS、Linux 和原生 Windows。当前只有 macOS 的运行和测试证据；设计可行不代表 Windows/Linux 已经支持。

## 3. 保留当前安装

### 3.1 已观察到的设置

已从安装的 LaunchAgent 与当前终端读取允许名单内的非敏感参数。没有读取凭据值、调用供应商或检查运行进程的完整环境。

| 项目 | 当前个人设置，应迁移保留 |
| --- | --- |
| 供应商 | Codex、Antigravity、OpenCode Go、ClinePass |
| 自动编排 | 已安装服务设置 `QUOTA_SENTINEL_ORCHESTRATOR_ENABLED=1` |
| 飞书 | 现有推送与机器人 |
| Codex 开窗 | Pi → 原生 Codex |
| Antigravity 开窗 | 原生 agy → Pi |
| OpenCode/ClinePass 开窗 | 直接 API |
| 四个供应商的额度查询 | 原生 → CodexBar 实时 → CodexBar 缓存 → Pi 快照 |

各通道预算、输入/输出上限、重试间隔和凭据引用也需保留。当前个人配置不加入新的 `pi-live` 查询通道。没有外层超时覆盖时，这份个人配置的现有推导上限为 6142.4 秒。

本轮已保存仅包含上述非敏感观察的本地文件：状态目录内 `migration-evidence/2026-10-02-observed-installation.json`，权限为仅本人可读写。该文件是迁移核对材料，目前不是生效配置。

### 3.2 迁移规则

1. 有有效配置文件：读取已有配置，不能重新套用新用户默认值。
2. 无配置但有旧安装证据：按旧代码的有效设置生成个人配置，先展示迁移预览；本次安装的观察材料用于对照。
3. 无配置也无旧安装证据：生成第 2 节的新用户默认值。
4. 旧状态目录、权威状态、锁记录和已安装服务都不通过“改默认值”重置。
5. 迁移只保存凭据引用，不复制令牌；重复执行迁移不覆盖已有配置。
6. 配置损坏、版本不支持或不同来源冲突时明确报错，不擅自当成新安装。

旧安装证据至少包括已安装的本软件后台服务、权威状态文件或旧配置；只有空目录不算旧安装证据。存在旧状态但无法确定服务偏好时，向导展示需要核对的项目，后台进程不得自行使用新默认值。

新用户需要独立的新安装初始化入口：只有显式的新安装操作成功创建全新的状态目录后，才可建立 JSON/Python 权威状态和初始配置。目录已存在但权威文件缺失时不凭空补建，改走核对或恢复流程；运行命令和后台启动都不能隐式初始化。此入口不复活原先移除的通用 `initialize_authority`，不改变旧安装的 bootstrap/cutover/rollback 契约。

已有个人配置中的数字固定保存，外层总预算根据这些数字与实际通道图重新推导，不能因为重构而漏掉认证、探测或清理成本。

## 4. 配置入口和依赖选择

使用一个有版本号的 JSON 文件，解析只依赖 Python 标准库。配置路径可以显式指定；macOS 迁移优先沿用当前状态目录内的配置位置。

用户入口：

- `quota-sentinel configure`：显示已有选择，交互修改并展示保存前的变化。
- `quota-sentinel config show`：展示实际生效的非敏感配置及其来源。
- `quota-sentinel config validate`：检查格式、能力组合和依赖；不调用模型，不主动刷新供应商凭据。
- 安装入口根据配置选择依赖和后台组件，启动时不临时安装软件。

新用户默认配置的结构示意：

```json
{
  "schema_version": 1,
  "origin": "new-installation",
  "features": {
    "automatic_opening": true,
    "quota_queries": true,
    "feishu_push": false,
    "feishu_listener": false
  },
  "providers": {
    "codex": {
      "enabled": true,
      "opening_enabled": true,
      "opening_chain": ["codex"],
      "quota_chain": ["native"]
    }
  }
}
```

未列出的供应商关闭。新建 JSON 会补全所选通道的预算和路径引用；示意中省略这些字段仅为方便阅读。已有配置中的缺省值迁移后必须具体化，不能随新版本默认值漂移。

配置优先级：当前命令明确参数 → 当前进程明确设置的兼容环境变量 → 保存的个人配置 → 仅新安装使用的默认值。环境覆盖会显示在 `config show`，不会写回个人配置。后台服务不得把旧版本内置默认值当成用户环境覆盖。

已知名称的非法能力组合、重复通道、已启用功能的空通道列表和非有限预算，在保存和运行入口拒绝。兼容旧 `QUOTA_SENTINEL_TRANSPORT` 时按旧行为转换成完整通道列表；未识别名称的兼容处理继续保持现有契约，向导新增配置则严格校验名称。

飞书推送用现有标准库 HTTP 实现；机器人所需的 `lark-oapi` 移入可选安装项。Linux 密码服务的库也属于可选安装项。核心命令在没有这些包时仍可导入运行。

## 5. 功能独立与内部依赖

四个用户功能独立选择：自动开窗、独立额度查询、飞书推送、飞书机器人。供应商也可只查询而不触发模型。

“只有开窗”的含义是关闭独立查询入口和飞书功能；自动开窗仍需要内部额度观察来确认窗口边界。向导把这个观察作为开窗的必需步骤明确展示，使用所选供应商的查询通道，不引入隐式 fallback。

如果用户要求完全禁止额度元数据请求，就不能启用当前依赖真实窗口边界的自动调度；可以保留手动单次触发。这一限制不能通过拿缓存假装最新读数绕过。

机器人单独启用时不自动启用后台开窗。机器人命令遵守相同功能开关：未启用的开窗或实时查询命令给出说明，不绕过开关去调用。

构建一个由有效配置派生的运行图，统一决定：

- 当前命令要构建哪些组件、允许操作哪些供应商。
- 检查哪些客户端、哪些凭据和哪些可选库。
- 额度采集、卡片展示和定时任务采用哪些供应商及通道。
- 单次尝试、探测阶段和整个 `check` 的最大耗时。

工厂按当前命令延迟构建组件。`usage` 不构建触发器，`status` 不需要模型认证，关闭飞书时使用空通知器并停止飞书凭据检查。

运行中的供应商列表可以缩小，但存储层完整供应商目录和历史数据保留。关闭供应商会停止未来调度，不删除它的历史；重新启用时先取得新的可信读数再恢复调度，不重放停用期间积累的任务。

## 6. 两条有序通道链

开窗链和查询链各自从前往后执行，首个符合现有成功标准的结果结束本轮。失败只进入显式列出的下一通道。

| 供应商 | 可选开窗通道 | 可选查询通道 |
| --- | --- | --- |
| Codex | `codex`、`pi` | `native`、`pi-live`、可用的 CodexBar 实时/缓存、Pi 快照 |
| Antigravity | `agy`、`pi` | `native`、`pi-live`、可用的 CodexBar 实时/缓存、Pi 快照 |
| OpenCode Go | `direct`、`pi` | `native`、`pi-live`、可用的 CodexBar 实时/缓存、Pi 快照 |
| ClinePass | `direct`、待新增适配的 `pi` | `native`、可用的 CodexBar 实时/缓存、Pi 快照 |

能力表来自实现，不能因为用户写了名字就视为支持。平台或客户端版本缺少某项能力时向导说明原因。`pi-live` 的三个供应商适配器只有通过第 7 节的查询契约后才列为可用。ClinePass 的 Pi 开窗适配需要作为本次新增能力实现并验证，当前代码仍只接受其直接 API 通道；这不意味着自动新增 ClinePass 的 Pi 实时查询能力。

选择 Antigravity 或 ClinePass 的 Pi 开窗通道，包括把 Pi 放在 fallback 位置，向导必须提醒安装对应的 Pi 插件，并显示插件名、安装指引和登录要求：

- Antigravity：`pi-antigravity`，安装指引 `pi install npm:pi-antigravity`，随后在 Pi 内完成对应供应商登录。
- ClinePass：首个适配目标为 `pi-clinepass-provider`，安装指引 `pi install npm:pi-clinepass-provider`，随后完成 ClinePass 认证。插件注册的 provider ID 与本软件逻辑名称要明确映射，不猜测其他插件的 ID。

向导显示安装指引，保存选择时生成依赖清单；安装阶段处理用户明确选定的依赖，运行阶段只检查，不下载插件。使用 Pi 通道前验证插件入口、供应商注册、目标模型和认证来源可用；缺失或不兼容时给出安装/更新指引，不能退回 Pi 默认供应商或默认模型。若链内有用户明确选择且可用的下一通道，可以按链继续；只有 Pi 时在模型调用前失败。未选择这些 Pi 通道时不检查对应插件。

当前用户的 Antigravity Pi fallback 继续引用已安装的插件；ClinePass 保持直接 API。迁移不会替用户安装新插件或加入新通道。

所有模型通道都成为独立执行器，去掉执行器内部隐藏的固定 fallback。Pi 与原生通道的两种先后顺序均可配置，不再只支持硬编码的一跳方向。

功能成功但成本超标继续按已修复的规则接受成功、记录告警，不再换通道重复开窗。原生 CLI 的完成事件、有效 usage 和成功回复等现有判断继续保留。

查询结果带来源、采集时间和新鲜度。缓存与已有快照始终不是实时读数；即使用户把缓存放前面，它也不能当作调度锚点。自动开窗必须配置至少一个具备实时能力的查询通道。

显示型查询按用户顺序取得首个可显示结果；调度型查询按同样顺序只接受实时结果，遇到缓存结果继续寻找显式链内的实时项，并保留缓存供展示。若没有有效实时结果，不更新真实窗口锚点。

## 7. Pi 实时查询：不触发模型

本机 Pi 0.99.2 的来源已核对。`prompt` 处理扩展命令时，只有命令存在才提前返回；不存在的 `/命令` 会继续进入普通输入流程。因此不能以发送未经验证的 `/usage` 来保证零模型调用。

现有三个采集扩展也不能直接满足要求：Codex 扩展读取模型回复头，另外两个扩展挂在 `agent_end` 上。

采用独立、受超时保护的 Pi 查询辅助程序：复用所选 Pi 安装提供的认证解析和供应商元数据 API，只返回规范化额度 JSON。程序不得调用 `session.prompt`、`stream`、`complete`、聊天端点或开窗执行器，也不启动交互式 Pi 会话。运行所需的认证接口和插件版本需先做兼容性检查；缺失时返回“实时查询不可用”。

各供应商的适配路径：

- Codex：使用 Pi 认证来源已有的账户认证上下文读取额度元数据，不用模型响应头。需要明确账户范围；缺少账户信息或可用访问凭据时返回失败。
- Antigravity：把现有 Pi 插件 `fetchAccountUsage` 查询与 `agent_end` 回调分离，独立调用并验证额度组。
- OpenCode Go：通过 Pi 所选的认证来源取得 API key，独立请求现有的只读额度端点。

不复制或覆盖官方客户端的认证文件，也不擅自兑换其他客户端拥有的共享 refresh token。认证确需刷新时仅走已验证、无模型调用且归属于该认证来源的接口；无法确认所有权则要求重新登录或进入用户明确配置的下一查询通道。

测试在发请求前拒绝所有模型端点，并给模型入口设置“调用即失败”的夹具。覆盖认证缺失、扩展缺失、版本不兼容、超时、错误负载和正常结果；只检查事后 token 为零不算足够证据。

Codex 原生仍用官方 app-server，新能力不会进入任何新用户或当前个人默认链。Pi 查询适配是显式可选项。

## 8. 平台适配

### 8.1 凭据

引入统一的凭据读写接口，调用方使用逻辑 service/account 名称。凭据读取、保存和错误路径都有期限，日志不含凭据值。

| 环境 | 凭据存放方案 |
| --- | --- |
| 当前 macOS | 继续使用现有 Keychain 服务名和账户名，兼容已有凭据 |
| Windows | Windows Credential Manager，使用用户会话的 Generic Credential |
| Linux 桌面 | 明确选定 Secret Service 或可用的 KWallet 后端，依赖按需安装 |
| Linux 无桌面服务器、容器或无密码库的环境 | 用户明确指定的环境变量或专用凭据文件 |

主配置只保存“到哪里取凭据”的引用。凭据文件是单独选择的存储方式，POSIX 检查所有者和访问权限，Windows 检查 ACL；不会静默退回权限不合格的文件或第三方明文密码库。

密码库调用可能出现解锁等待，因此通过有上限的隔离调用执行。后台拿不到凭据时给出可处理的错误，不永久等交互弹窗。

这些存储只管理本软件的飞书/API key 等凭据。原生 Codex/agy 和 Pi 的登录由各自客户端拥有，本软件保存位置引用，不把它们所有的 OAuth 令牌迁移成自己的凭据。

Windows 后台任务使用保存凭据的同一用户账户；不同登录会话可能不能读取该凭据。Linux 后台服务也需有对应 D-Bus 会话，或明确选择无桌面凭据来源。

### 8.2 进程、路径和锁

集中平台差异，避免各执行器重复判断操作系统：

- 可执行程序先读显式配置，再按当前平台查找 PATH。macOS 旧安装仍保留已生效路径。新 Linux/Windows 不要求 Homebrew。
- 临时目录使用系统临时目录，状态目录按平台选择；删除通用路径中的 `/private/tmp` 和 macOS 家目录布局假设。
- macOS/Linux 保留有期限的 POSIX 进程组回收；Windows 使用 Job Object 管理属于本次执行的进程树，确保受控归属建立后才允许子进程执行。超时、父进程退出和停止服务都必须清理后代。
- Windows 的管道读取使用支持匿名管道的有界读取实现，不能直接沿用 POSIX `selectors` 管道假设。
- 旧 macOS 状态继续使用相同 `shlock` 协议。Linux 新安装使用持有文件描述符的 POSIX 锁，Windows 使用文件范围锁；进程崩溃后锁自动释放。
- 状态目录记录锁协议标识。同一状态目录不能由不同锁协议的进程共同运行；离线搬迁只在所有服务停止后进行。
- 状态写入仍采用同目录临时文件和原子替换，核对三个系统的文件刷新与并发读写行为。

### 8.3 后台组件和安装

增加统一的 `quota-sentinel serve` 宿主，按配置启用调度器和机器人：

- 只开窗：启动调度器，不要求飞书机器人。
- 只机器人：启动机器人，不创建调度器。
- 两者都启用：同一宿主只创建一个调度器。
- 只做手动查询/手动触发：不安装后台服务。

macOS 使用 LaunchAgent，Linux 使用 systemd 用户服务，Windows 使用当前用户的计划任务。无 systemd 的 Linux 保留前台 `serve` 运行方式。安装、启动、停止、卸载都有清楚入口，不删除供应商状态或凭据。

现有 macOS 服务迁移需要一个明确的应用步骤：配置先可预览，完成测试后再更新服务入口；不能在生成配置或修改源码时顺便重启用户正在使用的服务。

可执行辅助脚本和资源必须打包进 wheel，摆脱只有仓库根目录才找得到它们的假设。旧根目录入口保留兼容包装，服务升级前后均可找到同一实现。

## 9. 实施边界与验收

这是共同的接口设计，后续拆为三个可验证的实施部分：

1. 配置、个人迁移、按需组件、显式链和飞书独立宿主；先在现有 macOS 安装保持兼容。
2. 独立 Pi 实时查询辅助程序及零模型调用验证。
3. 平台适配、安装入口及 Linux/Windows 原生验证。

每部分交付可测试的功能，不以只有开关或虚拟适配器冒充完整支持。平台宣称的范围按实际原生测试结果发布；仅在 macOS 上模拟 Windows 分支不能算 Windows 已验收。

最低验收场景：

- 新安装缺少 Pi、agy、CodexBar、飞书与系统密码库，只有已登录 Codex：原生开窗和原生查询可用，其他组件调用次数为零。
- 当前用户迁移前后，供应商、通道顺序、重试与超时参数、凭据引用和通知设置一致。
- 禁用功能后，不安装其可选库、不检查其凭据、不启动其进程；重新启用不重复执行旧债务。
- 单通道失败不会调用其他通道；`[pi, codex]` 和 `[codex, pi]` 分别遵守顺序。
- Antigravity/ClinePass 选择 Pi 为主通道或备用通道时均展示对应插件提示；插件缺失或注册不匹配时不会调用 Pi 默认模型。未选择 Pi 时不检查插件。
- 查询顺序独立可调，缓存保持非实时，调度锚点只取可信实时结果。
- Pi 额度查询各适配器的模型入口和模型端点调用次数为零，包括缺失或错误配置路径。
- 配置覆盖、无效配置、重复迁移、保存中断和并发读取不破坏已保存配置。
- 锁互斥、持有者崩溃恢复、超时清理以及停止服务后的后代进程清理在目标平台成立。
- 后台开窗不依赖飞书，组合运行只创建一个调度器。
- 安装 wheel 后从仓库外运行，所需辅助程序仍可找到。
- 核心导入保持标准库约束；可选库缺失时无关命令照常可用。

目标原生测试环境：当前 macOS、Ubuntu 22.04/24.04、Windows 11。供应商登录后的现场冒烟验证是单独步骤，不把受控假客户端的测试结果写成真实供应商已验证。

## 10. 可行性依据与证据边界

源码核查发现的平台耦合包括：`runtime/keychain.py`、`state/runlock.py`、`runtime/locks.py`、多个执行器的进程组清理、原生查询辅助程序的管道读取、固定目录和 LaunchAgent 安装器。因此跨平台不能只换一个密码读取函数。

外部依据只支持可行性判断：

- [OpenAI 官方 Codex CLI 文档](https://learn.chatgpt.com/docs/codex/cli)有 macOS/Linux 和 Windows 安装入口；[官方 Windows 文档](https://learn.chatgpt.com/docs/windows/windows-sandbox)说明可以原生运行 Codex CLI。
- [Google 官方 Antigravity CLI 仓库](https://github.com/google-antigravity/antigravity-cli)提供 macOS/Linux 与 Windows 安装入口。这不证明本仓库当前版本的参数和清理方法已经兼容 Windows。
- [Microsoft 的 CredReadW 文档](https://learn.microsoft.com/en-us/windows/win32/api/wincred/nf-wincred-credreadw)提供用户会话凭据读取接口，并说明登录会话限制。
- [Python keyring 文档](https://keyring.readthedocs.io/en/stable/)列出系统密码后端与无桌面 Linux 的 D-Bus 条件；无桌面不等于天然有可用、已解锁的密码库。
- [CodexBar 的查询实现说明](https://github.com/steipete/CodexBar/blob/main/docs/codex-oauth.md)展示只读额度端点及认证所有权约束，供 Pi 查询适配参考；它不是 Pi 官方实时查询能力或稳定公开 API 的承诺。
- [pi-antigravity 的安装文档](https://github.com/Rahularya01/pi-antigravity)和 [pi-clinepass-provider 的安装文档](https://github.com/jellydn/pi-clinepass-provider)提供对应插件安装入口。ClinePass 文档展示了 `clinepass` provider 和 `cline-pass/deepseek-v4.1-flash` 模型；本次尚未在本软件中运行或验证该插件。

本轮未请求真实额度、未调用真实模型、未读取密钥、未重启服务。前一轮三个缺陷的修复及 22 个回归脚本验证保持原样；本设计不声称这些新功能已经实现。
